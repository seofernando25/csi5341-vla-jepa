# Reporting results

A result is reportable only if every applicable item holds. Otherwise label it preliminary and
name the missing item.

## Provenance

- [ ] The number comes from a committed record under `studies/` (run JSON, episodes CSV or
      milestone JSON), not from a terminal log.
- [ ] The record names the checkpoint revision/SHA-256, code revision, configuration, GPU and seeds.
- [ ] Figures are regenerated by a committed script (`report/figures.py`) from those records.

## Protocol

- [ ] Arms share task suite, initial states, per-episode seeds, action horizon, flow steps,
      step limit, GPU and software versions. Differences are stated.
- [ ] Phase is explicit: smoke (10 trials), development (100) or reserved (500). Never pool
      phases. Reserved trials never guide selection.
- [ ] Runtime failures (OOM, crashes) are reported separately; they are not task failures and
      not architecture evidence.

## Statistics

- [ ] Success has a Wilson 95% interval and trial count.
- [ ] Differences from B16 use the task-stratified paired bootstrap on identical states,
      with gain/loss counts.
- [ ] A 10- or 100-trial result is not used to claim a small difference.
- [ ] Per-task breakdown is checked: one task (LIBERO-Spatial task 5) can drive the aggregate.

## Efficiency

- [ ] Latency: synchronized, after warm-up, simulator excluded; median and p95; state whether
      preprocessing is included.
- [ ] Memory: name the quantity (peak allocated, peak reserved, NVML process) and the unit.
- [ ] Separate savings from quantization, structural removal and dropping the unused world model.

## Claims

- [ ] Held-out loss and offline action error are not task success.
- [ ] Say whether the result is a replication, new evidence or a negative result.
- [ ] Follow the `terse-writing` skill: number, basis, comparison, caveat.
- [ ] Use a `CORR` board record when a result changes an earlier claim.
