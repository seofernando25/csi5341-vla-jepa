# Dream-RSI Reference (`arXiv:2609.14858v2`) and `rsi/` Fidelity Map

Distilled specification of Tong Zheng et al., *"Dream-RSI: Recursive Self-Improvement through Evolving Worlds"* (`arXiv:2609.14858v2`, 2026-10-06) and exact comparison with `rsi/`.

## 1. Paper Architecture (Section 3, Appendix B.2, Appendix D)

The paper states **no numbered Algorithm**; the method is defined by Section 3, Eq. (1), Table 3, and Appendix D Listings 1–2.

Dream-RSI closes a recursive self-improvement loop at the **exploration-policy layer** ($\pi_t$), keeping the underlying base LLM, evaluator, and execution interfaces fixed:

1. **Discovery tree and batch interface:** A tree $\mathcal{T}$ is rooted at $r$ ($s_r = 0$). Each non-root node $v$ has one primary parent, resumes that parent's saved filesystem snapshot and history, runs the discovery agent once, stores its own snapshot and evaluation score $s_v$, and becomes a selectable leaf. Eligible actions are $A(\mathcal{T}) = \{r\} \cup \text{Leaves}(\mathcal{T})$; with $W \ge 1$ parallel workers, the exploration policy selects a batch $C \in A(\mathcal{T}; W) = \{C \subseteq A(\mathcal{T}) : |C| \le W\}$.
2. **Online rollout (Section 3; Appendix D.1 Listing 1):** At iteration $t$, policy $\pi_t$ drives a discovery agent for up to $K_1$ rounds. For each $v \in C_t^k$, a worker inspects every prior `proposal.md`, `eval/score.json`, and `error.txt` in full, writes a new `proposal.md` and `$eval_program`, evaluates it, and attaches the child node to $v$. When finished, $\mathcal{T}_t$ joins history $\mathcal{H}_t = \mathcal{H}_{t-1} \cup \{\mathcal{T}_t\}$.
3. **Offline replay ("dreaming", Section 3; Appendix D.2):** Each recorded $\mathcal{T}_i \in \mathcal{H}_t$ becomes a deterministic replay simulator (abstracted in Appendix D.2 as an irregular branch $\times$ attempt grid). Replaying policy version $\pi_t^m$ under budget-control knob $\rho \in \mathcal{R} = \{0, 0.25, 0.5, 0.75, 1\}$ reveals already-stored children $\text{Child}(v; \mathcal{T}_i, \mathcal{T}_{i,\rho}^{m,k})$ for up to $K_2$ rounds. No discovery agent or evaluator re-runs offline.
4. **Eq. (1) replay objective (Section 3):** Let $B_i = |\mathcal{T}_i| - 1$, $S_i = \max_{v \in \mathcal{T}_i \setminus \{r\}} s_v$, $n_{i,\rho}^m = |\mathcal{T}_{i,\rho}^{m,k_{i,\rho}^{m,\star}}| - 1$ calls, and $a_{i,\rho}^m = \text{clip}(s_{i,\rho}^m / S_i, 0, 1)$. Over the nondominated quality–cost frontier $(\bar{n}_{i,j}^m, \bar{a}_{i,j}^m)_{j=1}^{L_i^m}$ ordered by increasing $\bar{n}$ ($\bar{a}_{i,0}^m := 0$):
   $$V_i^m := \frac{1}{B_i}\sum_{j=1}^{L_i^m} (\bar{a}_{i,j}^m - \bar{a}_{i,j-1}^m)(B_i - \bar{n}_{i,j}^m) - \lambda \frac{1}{|\mathcal{R}|} \sum_{\substack{\rho \in \mathcal{R} \\ n_{i,\rho}^m > 0}} \frac{k_{i,\rho}^{m,\star}}{n_{i,\rho}^m}$$
   In Appendix D.2 Listing 2, `effective_sequential_rounds` increments by $\lceil |C| / W \rceil$ per batch, so serial batches score penalty $\approx 1$ and full batches approach $1/W$.
5. **Policy improvement and monotonic selection (Section 3; Appendix B.2; Appendix D.2):** Starting from $\pi_t^0 = \pi_t$, a **policy-development agent** inspects archived replay execution traces (`policy_execution_traces.jsonl`), `beta_sweep.json`, and `live_cycle_manifest.json` sidecars, then rewrites executable Python (`OptimalPolicy.solve` and `plan_grid`) into $\pi_t^{m+1}$ for $M-1$ steps ($M=4$ total in Table 3). Next deployment is $\pi_{t+1} = \pi_t^{m^\star}$ with $m^\star \in \arg\max_m \frac{1}{t}\sum_{i=1}^t V_i^m$, guaranteeing $V^{m^\star} \ge V^0$ on $\mathcal{H}_t$.

### Appendix D.2 Interface & `beta` Contract

- **Prefix-only invariant:** Decisions use only `question.observed()`, `legal_actions()`, `legal_roots()`, `opened_branches()`, `meta(cell_id)`, `baseline_score`, and `max_parallelism`. `best_so_far` and `budget_spent` are bookkeeping only.
- **Three roles of `beta` ($\rho$):** (1) fixed scalar inside `_schedule(beta)` during one episode; (2) swept across $\{0, 0.25, 0.5, 0.75, 1\}$ during offline replay; (3) updated once between live cycles from manifests and sweeps (default `0.6` when history is insufficient).
- **`plan_grid(context) -> GridPlan`:** Runs before each live cycle to bound `(branch_count, refine_count)` capacity from the prior cycles' manifests and beta sweeps; it does not pre-generate the candidates inside those slots. The request is clamped to the protocol caps (probe budget, `max_parallelism`, GPU slots, `rounds_cap`), and an unusable request falls back to the pre-registered plan, which is also what a policy returns with no history.

### Known deviations

Nine deviations the table above does not state, as of 2026-11-15:

- **Live-CUDA floor.** Resident bytes are `max(tensor walk, live CUDA bytes of the process)`, so a compressed copy beside the original scores ~0 ([evaluation/compression/solution.py](../evaluation/compression/solution.py)).
- **No replay probe budget or round cap.** Replay calls `solve(..., budget=None)` and `ReplayQuestion` has no round limit; the policy must stop itself ([rsi/objective.py](../rsi/objective.py), [rsi/tree.py](../rsi/tree.py)).
- **Replay parallelism is the CLI flag.** `--max-parallelism` defaults to 4 and is passed straight to replay; the live cycle uses `min(CLI, protocol)` = 2 ([rsi/__main__.py](../rsi/__main__.py), [rsi/durable_loop.py](../rsi/durable_loop.py)).
- **Beta is not updated between cycles.** `recommend_next_beta` is never called; each cycle records only `baked_in_beta` ([rsi/dream.py](../rsi/dream.py), [rsi/online_cycle.py](../rsi/online_cycle.py)).
- **Smoke is not a separate state set.** Both phases roll out on the development states and seeds, 1 vs 10 episodes per task ([evaluation/compression/solution.py](../evaluation/compression/solution.py)).
- **The development gate is recorded for promoted nodes only.** `promote_top_k` writes `development.json`; no selection reads it ([rsi/online_cycle.py](../rsi/online_cycle.py), [rsi/expansion.py](../rsi/expansion.py)).
- **Lambda and the beta grid live in code.** `0.05` and `(0.0, 0.25, 0.5, 0.75, 1.0)` are defaults in [rsi/objective.py](../rsi/objective.py), now also recorded in [studies/program-v1/protocol.json](../studies/program-v1/protocol.json); replay does not read the protocol values.
- **The policy agent runs code.** The paper fixes its inputs, output and step count, not its tools. We chose `read,write,edit,bash`, repo source read-only at `/tmp/repo`, a GPU, network, a writable `/tmp/pkgs` and a runnable in-sample replay, so it can measure before it answers; the prompt gives it half of each step's wall clock for exploration. The harness still replays, audits and selects; the agent's own numbers are never read. Held-out worlds are generated after the agent exits and are never mounted; `rsi/synth.py` is withheld from its source mount, so it cannot regenerate them from the repo. Cycles `iter_000`..`iter_002` ran under the earlier `read,write,edit` rule.
- **Policy-step repairs.** A step that fails validation, or that replays without improving in-sample $V$, gets one repair attempt with the failure or the delta in its prompt. $M-1$ accepted steps are unchanged, but the agent can run up to $2(M-1)$ times. A timed-out step is scored on the `method.py` it left behind (`timeout_salvaged`, accepted only if it passes the audit and beats the incumbent), with its cost and transcript kept ([rsi/policy_dev.py](../rsi/policy_dev.py)).

## 3. Reporting & Provenance Boundaries

- **Node outputs:** `proposal.md` and `solution.py` are both required; a node without a readable `proposal.md` fails as `implementation_failure` before evaluation, while a placeholder-only (`[object Object]`) transcript is `agent_failure` and is never evaluated. Agent cost and turns come from the full stream, summarized in `logs/agent_result.json`; each cycle manifest and the loop state record the run arguments and provenance (code revision, protocol hash, checkpoint revision, GPU, environment, seed, suite, policy hash).
- **Provenance:** The pre-cleanroom Dream-RSI records and policy revisions were deleted from the working tree on 2026-11-15 and remain in git history at tag `pre-cleanroom-20261115`. They are not reused or cited. Fresh full-loop runs live under `studies/program-v1/` via `vla-rsi cycle`, `vla-rsi develop`, and `vla-rsi loop` (detached: `vla-rsi start`, `status`, `stop`). The clean protocol uses a pre-registered static `GridPlan`; it does not use the old adaptive planner or `gate_retry`.
- **Replay $V$ vs. LIBERO accuracy:** Replay objective $V$ scores exploration policies over frozen `DiscoveryTree`s using gate-qualified size reduction; actual task performance is measured only by LIBERO rollouts (`smoke`, `development`, and manual post-search `final`).
- **Sandbox boundary:** Mounts, network and fail-closed behavior are in the §2 table ([rsi/sandbox.py](../rsi/sandbox.py)). The `--no-bwrap` flag and the host-loaded selected policy are the two known gaps.
- **Residual risks** (open, not mitigated):
  - The agent shell shares the host network (`--share-net`); the agent needs its API.
  - The agent can read its backend credentials: the pi `auth.json` (bound read-only at `/tmp/pi-agent/auth.json`) or the Claude Code credentials file (bound read-only at `/tmp/.claude/.credentials.json`).
  - The GPU slot lock is cooperative: an agent can run GPU code without `rsi.gpu`.
  - GPU sandboxes (agent and evaluator) have no memory or process-count limit; only the wall-clock timeout applies.
  - Nested user namespaces are possible.
  - Integer look-up tables keyed on root count, with (branch, attempt) values, pass the audit (red-team F6). Held-out reporting is the only check.
  - The selected policy runs in the host process during a live cycle, behind the audit and `PrefixView`.
  - Smoke (10 episodes) is noisy. The untouched policy scored 8/10 in one sandboxed run on 2026-11-15, exactly at the gate (`smoke_min_successes`: 8).
  - The policy agent can run code and read the repo, so its in-sample $V$ is self-measured; only the harness replay is recorded. Withholding `rsi/synth.py` keeps the held-out worlds out of the mount, but a determined agent could reimplement the generator from the family names, so held-out numbers stay reported, never used for selection.
  - The policy agent's workspace and package dir are not size-capped beyond the 256 MiB workspace check; `/tmp/pkgs` is per step and gitignored.
